# 既存アプリケーションをNagi OSへ移植する

このガイドは、既存のRust、C、C++アプリケーションで動作しているコードを再利用しながらNagi OS向けに移植する開発者を対象とします。Linux実行ファイル、POSIXプログラム、GUIフレームワークが変更なしで動くことを保証するものではありません。

## 1. 変更前にソースを調べる

アプリケーションのルートで、ホスト側の静的スキャナーを実行します。

```text
nagi port readiness PATH/TO/PROJECT --format json
```

NagiOSのソースチェックアウトを使う場合は、CLIをインストールせず、任意の作業ディレクトリから次のように起動できます。

```text
cargo +nightly-2025-08-01 run --locked --offline --manifest-path PATH/TO/NagiOS/tools/nagi-bootstrap/Cargo.toml -- port readiness PATH/TO/PROJECT --format json
```

ビルド・起動するのはホスト側のNagi CLIだけです。検査対象アプリはビルドも実行もしません。

コマンドはソースと認識済みマニフェストを読み取ります。対象プロジェクトのビルドシステム、ビルドスクリプト、コンパイラー、パッケージマネージャー、実行ファイルは起動しません。バージョン付きJSONレポートには、検出した言語、一部のマニフェストと直接依存、ソース上の限定的な根拠、スキップ・上限超過の情報、制約を出力します。検出項目は人による確認の手掛かりであり、項目がないことは移植可能性の証明ではありません。

初期実装では、一般的なRust/C/C++の拡張子、Cargoとpackage JSONの依存、CMakeの基本的な`find_package`/`pkg_check_modules`、Makefileの`-l`ライブラリ名を認識します。ファイル数とサイズに上限を設け、シンボリックリンクや生成物・vendorディレクトリを読み飛ばし、単純なテキストパターンを使います。走査中にパスが置き換わらないよう、プロジェクトツリーを変更せず実行してください。走査中の同時置換を防ぐロックはありません。推移依存の解決、ビルド言語の完全な解析、マクロや生成ソース、ライセンス適合性、実行時の挙動は確認しません。lockfile、ビルドスクリプト、ネイティブライブラリ、フレームワークの使用状況は別途確認してください。

## 2. 境界の負荷を見て最初の移植対象を選ぶ

ソースと依存を適法に再利用でき、テスト可能な小さな単位から始めます。以下は計画時の目安です。実際の工数はコードと利用できるNagi公開APIによって変わります。

| ソースの構成 | 初期の移植負荷 | 最初に確認すること |
| --- | --- | --- |
| 依存の少ないRustのドメイン／モデルコード | 比較的低いことが多い | `std`のファイル・プロセス・ネットワークAPI、build script、ネイティブcrate、target依存コード |
| 標準Cのみを使うCライブラリ | 低〜中程度のことが多い | libc前提、コンパイラーフラグ、リンク、所有権とエラー境界 |
| POSIXまたはOS固有APIを使うCコード | 中〜高 | ファイル・プロセス・スレッド・ネットワークAPI、システムヘッダー、ネイティブ依存、権限 |
| GUIフレームワークなしのC++コア | 中程度、ツールチェーン依存 | 標準ライブラリ／ツールチェーン、例外／RTTI、ネイティブ依存、ABI前提 |
| Qt、GTK、Electron、SDLなどのGUI／フレームワーク統合 | 高いか、実証まで不明 | フレームワークサービス、ウィンドウ・入力・描画経路、プラグイン、ネイティブ依存 |

スキャナーは`std::fs`、`fork`、`pthread`、`QApplication`などの根拠を出せますが、フレームワークやABIがサポートされているとは判断できません。この分類だけから移植日程を見積もらないでください。

## 3. 再利用するアプリケーションロジックとOSアダプターを分ける

可能ならデータモデル、検証、パーサー、アルゴリズム、業務ルールをOS非依存のコアに保ちます。ファイルアクセス、プロセス起動、ネットワーク、UI描画、デバイス、永続化、プラットフォーム固有スレッド処理は明示的なアダプターに分けます。境界を一つずつ移植し、コアの既存テストを維持します。

[`portable-files`サンプル](../../../samples/porting/portable-files/README.md)は、`apps/nagi-files/src/model.rs`の`Location`と`FileName`の検証を適応したものです。カタログはメモリー上だけで動きます。ドメインコードの再利用例であり、Nagiのファイルプロバイダー、ホストファイルシステムアクセス、インストール可能なアプリではありません。

## 4. プラットフォーム処理をNagiの公開契約に結び付ける

機能に適した公開Rust SDKまたはC境界と、文書化された公開APIレベルを使います。ファーストパーティとサードパーティは同じ公開APIを利用します。ファーストパーティ内部実装、非公開サービス、暗黙の特権には依存しないでください。

必要なCapabilityだけを目的とともに要求し、保護された処理はNagiのPermission/Capability契約を通します。ホストの暗黙権限をアプリへ黙って引き継がないでください。保護された作用がない間に限り、サンプルのようなゼロCapabilityのマニフェストが適切です。

## 5. ホスト検証とターゲット検証を段階的に行う

リポジトリルートから、portable-filesサンプルのホストテストとビルドを実行できます。

```text
cargo test --manifest-path samples/porting/portable-files/Cargo.toml
cargo build --manifest-path samples/porting/portable-files/Cargo.toml
cargo run --manifest-path tools/nagi-pkg/Cargo.toml -- manifest validate samples/porting/portable-files/manifest.json
```

この手順で確認できるのはホスト側のコンパイル／テストとマニフェスト構造の検証だけです。このfixtureはインストール可能なNagiパッケージではありません。ホストビルドの成功はターゲットビルドではなく、マニフェスト検証はCapabilityを付与せず、起動動作も証明しません。

該当するNagiのリリースゲートとランタイムゲートが開くまでは、ゲストへのインストール、起動、実行時受け入れ試験を行いません。ゲート開放後は、実際のターゲット成果物、要求Capability、Permission表示、APIバージョン、失敗・復旧経路を検証します。それまでは未実施として記録してください。

## この手順が保証しないこと

- Linux実行ファイル、一般的なPOSIX、libc、ABIの互換性。
- ターゲット上での実証を伴わないQt、GTK、Electron、SDLなどの互換性。
- readinessレポートに検出項目がない場合の互換性認定。
- ホストテストやマニフェスト検証によるゲストインストール／起動。

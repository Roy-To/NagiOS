# レビュー・統合・止まったときの再開

## 1. 人間とAIの役割

Core Developerが担当内の判断とレビュー結果に責任を持ちます。Claudeの実装をCodexへ、Codexの実装をClaudeへレビュー依頼できますが、別AIが同意したことだけで品質を証明しません。実際の差分・テスト・境界を確認します。

DEC-049のDeepSeekレビュー方針を、Claude/Codexの相互レビューで実施済みに置き換えません。既存の認可済み担当へ渡す経路を開始時に決めます。資格情報を友人へコピーしません。未実施なら未実施と報告し、元方針にない独自の全面停止条件を追加しません。merge条件は実際の指定先・保護・承認に従います。

## 2. レビューに渡す最小情報

```text
TASK: NDP-xx
BASE: 実在する比較元commit
HEAD: レビューする固定commit
SCOPE: 承認済みpath
TESTS: 実行コマンドと結果、host/targetの別
OPEN: 未検証・既知の不足
```

編集者を止めずにレビューするなら固定HEADを別の読取用作業場所で参照します。同じフォルダでレビュー中にbranchを切り替えたり、自動修正を始めたりしません。指摘の修正は元の実装担当へ戻すか、編集権を明示的に交代します。

## 3. レビューの重点

PT-01の二重実装、存在しないSDK参照、対象外ファイルの走査・上書き、コメントや文字列の誤検出、巨大/壊れた入力、UIイベント未接続の成功表示、無許可subprocess、host成功とtarget成功の混同を確認します。正常系だけでなく、拒否・未対応・部分失敗を実装から検証します。

## 4. commitとPR

差分を確認して担当ファイルだけをstageします。無関係な変更をまとめて `git add .` しません。現在の開始許可が認めるbranchへcommit/pushし、指定baseへPRを出します。共有branchへのforce-pushやmainの直接変更はしません。

PR本文は次で足ります。

```text
目的: NDP-xx の最小成果
変更: 担当pathと接続する既存契約
確認: コマンド / 成功・失敗 / host-only
残件: 未実装・未検証・ownerへの依頼
```

CIが古いmilestone、共有登録、環境により止まった場合は原因を分けます。自分の機能のテスト成功とCI全体成功を混同せず、CIを通すために共有gateを削除しません。小さな独立成果を次々に提出します。

## 5. 統合

NDP-12で指定Integration Ownerが統合します。承認された分野内branchでの統合と上流mainへのmergeは別です。Linux移行の統合branchを名前だけで自分のmerge先にしません。競合解消時に片方の機能や失敗テストを落とさず、影響するテストを再実行します。

## 6. 停止・利用枠切れ・端末変更

進行中の差分を消さず、実在するcommit、未commitの有無、実行結果、次の作業を短く残します。新しいセッションで `prompts/04_RESUME.md` を読み、実際のbranch/status/diffを確認して再開します。過去チャットの「終わった」は証拠にしません。

同じ障害を意味なく繰り返し試しません。DEC-049に従い、3回の異なる修正で解けなければ原因と次の候補を記録し、別の許可済みtaskへ移ります。認証拒否や不明な結果を別アカウント・別経路で迂回しません。
